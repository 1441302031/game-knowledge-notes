🏗️ 阶段一：分布式系统基石（第 1–2 周）

面试官看到你用了 etcd-client 依赖，一定会问：「你们怎么用 etcd 做服务发现的？节点宕机了怎么处理？」——你必须能答上来且有代码支撑。

1.1 服务发现 → 落地到 Ares

目标：把 etcd 从依赖变成真正可工作的服务发现层
子任务时间产出
学习 etcd 核心概念：lease、watch、kv、prefix 2天 能讲清 etcd 如何保证 CP
实现 ServiceRegistry：启动注册 + 心跳续约 + 优雅下线 2天 各服务启动时自动注册到 etcd
实现 ServiceDiscovery：watch prefix + 本地缓存 + 健康检查 2天 Gateway 动态发现 Game/Room/Battle 实例
处理节点宕机：lease 过期自动剔除 + Gateway 重连逻辑 1天 节点挂掉不影响系统运行
编写服务发现集成测试 1天 test_service_register_deregister

面试回答模板

我们使用 etcd 的 lease 机制做服务注册，每个节点启动时用 30 秒 TTL
注册到 /ares/services/{service_type}/{node_id}，每 10 秒续约一次。
Gateway 通过 watch 这个 prefix 实时感知节点上下线，本地缓存一份
endpoint 列表，路由时用 LeastLoaded 策略选择目标节点。

如果 etcd 宕机了怎么办？—— 每个节点本地有 fallback 配置列表，
etcd 不可用时降级为静态路由。这是我们实现的优雅降级。

1.2 一致性 → 理解 Raft

目标：能画图解释 Raft 的 Leader Election + Log Replication
子任务时间产出
看 Raft 可视化动画，理解选举/日志复制/快照 1天 能手动推演选举过程
阅读 etcd 如何基于 Raft 工作 1天 理解 etcd 是 CP 系统
理解 CAP 定理，能对号入座 0.5天 学会说「Gateway 是 AP，MatchEngine 是 CP」

面试回答模板

游戏服务器的不同模块对一致性的要求不同：
- 匹配引擎：需要强一致性（CP），用 etcd 的原子操作保证不会重复匹配
- Gateway 路由：可用性优先（AP），允许短暂路由到旧节点
- 房间状态：最终一致性即可，通过 etcd watch 收敛

我们利用 etcd 的 conditional update 实现了分布式锁，确保匹配结果
不会被两个 Game 节点同时消费。

Schema 设计建议

-- 账号表
CREATE TABLE accounts (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    account VARCHAR(64) UNIQUE NOT NULL,
    password_hash VARCHAR(256) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    last_login_at TIMESTAMP NULL
);

-- 玩家表（一个账号可有多个角色）
CREATE TABLE players (
    id BIGINT PRIMARY KEY,
    account_id BIGINT NOT NULL REFERENCES accounts(id),
    nickname VARCHAR(32) NOT NULL,
    mmr INT DEFAULT 1000,
    level INT DEFAULT 1,
    total_matches INT DEFAULT 0,
    win_count INT DEFAULT 0,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 对局记录
CREATE TABLE battle_records (
    id BIGINT PRIMARY KEY,
    battle_id BIGINT NOT NULL,
    player_id BIGINT NOT NULL,
    hero_id INT,
    team_id INT,
    kills INT DEFAULT 0,
    deaths INT DEFAULT 0,
    assists INT DEFAULT 0,
    result ENUM('win', 'lose', 'draw'),
    mmr_change INT,
    played_at TIMESTAMP NOT NULL,
    INDEX idx_player (player_id, played_at)
);

3.2 Actor 模型

目标：能用 Actor 模型重构 Ares 的部分模块，并解释为什么
子任务时间产出
理解 Actor 模型：消息传递、无共享状态、监督树 1天 能对比 Erlang/Akka/Actix
用 tokio::mpsc 实现一个简单的 Actor 框架 2天 PlayerActor / RoomActor
对比 Ares 当前的 Arc<RwLock<>> 模式 vs Actor 模式 0.5天 形成自己的观点

面试回答模板

Ares 目前使用 Arc<RwLock<>> 的共享状态模式，对于低并发场景足够了。
但如果我们把每个 Player 抽象为一个 Actor，消息驱动的方式有几个好处：
1. 锁争用更少 —— 每个 Actor 独占自己的状态
2. 天然的并发隔离 —— 不需要到处加锁
3. 更好的容错 —— Actor 崩溃不影响其他 Actor

不过 Actor 模式也有代价：消息队列可能堆积、调试更复杂。
在 Ares 中，BattleServer 里的每个 BattleInstance 就是天然的 Actor 候选。

5.2 专题深度：帧同步

这是你的核心优势区。Ares 实现了 Lockstep，面试官会深挖。

必须掌握的概念（能画图 + 写伪代码）

  • Bucket Sync：为什么需要输入延迟缓冲区？buffer_size 怎么定？
  • 确定性：浮点数确定性问题，固定随机种子，排序一致性
  • 追帧：客户端落后时怎么追？快放 vs 跳帧
  • 断线重连：重连后怎么恢复到当前帧？（快照 + 增量帧）
  • 观战：观战者只需要帧数据，不需要发送输入
  • 录像回放：帧数据的存储和重放

面试回答模板

我们使用 Bucket Sync 模式：客户端提前 N 帧发送输入，服务器在缓冲区
收集后广播。这样即使网络抖动 100ms，在 20fps 下就是 2 帧的缓冲，
玩家不会感觉到卡顿。

我们设置 input_delay_frames = 3（20fps 下 = 150ms），这个值基于
压测的 P99 延迟数据动态调整。

如果某个玩家的输入迟迟不到，服务器填入空输入（上一帧的输入），
保证帧循环不会停滞。这个设计的 trade-off 是：网络差的玩家会
出现短暂的「角色不动」，但其他玩家不受影响。

5.3 万人同屏

这是一个经典的面试题，展示你的 AOI + 空间划分知识。

子任务时间产出
学习空间划分算法：Grid / QuadTree / Spatial Hash 1天 能画图对比三种算法
在 Ares 的 StateSyncEngine 中实现 Grid AOI（替换当前 O(n²)） 2天 AOI 查询从 O(n²) → O(1)
理解 Cross-Server AOI：跨节点的实体可见性怎么处理 1天 能讨论边界跨越方案

面试回答模板

对于万人同屏场景（如国战 MMO），我们用 Grid AOI 将地图划分为
N×N 的格子。每个实体注册到所在格子，查询时只需检查 9 个相邻格子。

为什么不用 QuadTree？—— Grid 在实体密集时更可预测，不会出现
树不平衡的问题。QuadTree 适合实体稀疏分布的场景。

更进一步，当单节点无法承载全部实体时，我们用 Cell-Server 模型：
每个地图区域分配给不同的 BattleServer，边界区域的实体同步到
相邻节点。这本质上是空间分片。

💬 30 秒项目介绍模板

我做了一个分布式游戏服务器框架叫 Ares，用 Rust 写的。
它是 5 个微服务组成的分布式系统：Gateway 负责 TCP 接入和消息路由，
Game/ Match 负责登录和 ELO 匹配，Room 管理房间生命周期和 Battle 分配，
Battle 实现了三种同步模式——Lockstep 帧同步、StateSync 状态同步和
Hybrid 混合模式。

整个项目 7 个 crate，36 个集成测试全部通过，压力测试下零超时零错误。
我负责全栈：从 Proto 协议设计、分布式服务发现、匹配算法、到 Unity
客户端 SDK。这个项目帮我深入理解了分布式系统的一致性模型、游戏同步
的核心 trade-off，以及 Rust 异步生态的实际应用。
