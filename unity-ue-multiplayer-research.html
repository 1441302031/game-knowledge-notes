Unity vs Unreal Engine 多人游戏框架调研

为 Ares（Rust 游戏服务器）构建客户端框架

调研日期： May 2026 背景： Ares 是一个基于 Rust 的分布式游戏服务器框架，支持 Lockstep（帧同步）、StateSync（AOI）和 Hybrid 模式，使用自定义 TCP+Protobuf 协议和 gRPC 内部服务通信。

1. Unity 多人游戏框架对比

1.1 Mirror Networking

  • Stars: 6,182 | License: MIT | Production Games: Population: ONE（被 Meta 收购）、1000+ 款 Steam 游戏
  • Architecture: Client-Server 模型。服务端和客户端是同一个项目，使用 NetworkBehaviour。使用 [SyncVar], [Command]/[ClientRpc]/[TargetRpc] 属性配合 IL 后处理实现零开销 RPC。
  • Sync Model: State Sync （权威服务器）。服务器拥有状态，通过 SyncVars + SyncLists/Dicts/Sets 同步到客户端。没有内置 Lockstep/帧同步支持——必须自行构建。
  • Dedicated Server: 完整的专用服务器支持。服务器可以在 Linux 上以 headless 模式运行。
  • Rust/Ares 集成：⭐⭐⭐⭐（良好）
  • Mirror has a well-defined abstract Transport class (ArraySegment<byte> send/receive). Writing a custom AresTransport : Transport is straightforward.
  • 传输层完全可替换——Mirror 自带 Telepathy（TCP）、KCP、Libuv 等。
  • 策略：编写一个自定义 Transport，将 Mirror 消息序列化为 Ares Protobuf 帧，通过 TCP 路由到 Ares Gateway，并将响应反序列化回来。 Unity 客户端成为一个"瘦客户端"——Mirror 处理 Unity 端的网络惯用模式（NetworkBehaviour、SyncVar、RPC），但所有实际游戏逻辑运行在 Ares 上。
  • 一个注意事项：Mirror 的内置状态同步（SyncVars）会与 Ares 的 StateSync 冗余——你使用 Mirror 主要是为了它的 RPC/command 基础设施和传输抽象，而不是它的状态复制。
  • 快照插值: 稳定。 Lag Compensation: Beta 阶段。 客户端预测: 研究阶段（尚未发布）。

1.2 FishNet（FirstGearGames）

  • Stars: 1,934 | License: 自定义（<20 CCU 免费，更大规模需付费 Pro）| Production: Growing rapidly
  • Architecture: Client-Server 模型，具有 Progressive 功能集。使用 Transport 基类进行传输抽象。支持多个同时传输。
  • Sync Model: Advanced State Sync ，支持基于 tick 的同步、增量压缩和带宽优化。支持按组件进行服务器权威和客户端权威。
  • 关键差异化特性：
  • Client-side Prediction: 内置预测系统（少数有此功能的 Unity 网络代码之一）。
  • 服务端和解: 内置对预测对象的和解。
  • Lag Compensation: 内置（回溯时间以验证命中）。
  • Scene Management: 高级场景加载/卸载，带有网络对象生命周期。
  • Progressive Tick System: 可变 tick 频率、带宽管理。
  • Nested Network Objects: 正确的父子网络 Transform。
  • Dedicated Server: 完整的 Linux headless 支持。
  • Rust/Ares 集成：⭐⭐⭐⭐⭐（最佳）
  • 与 Mirror 相同的 Transport 抽象——自定义 AresTransport 实现简洁。
  • FishNet 的预测与和解系统是 Ares 集成最有价值的功能。既然你在客户端框架中无论如何都要编写预测/和解逻辑，FishNet 为你提供了一个经过实战检验的实现，可以直接使用或作为参考研究。
  • FishNet 的 tick 系统与 Ares 的 frame/Lockstep 模型天然对齐。
  • Pro 许可证限制（免费版 <20 CCU）需要考虑，但开发/测试免费，且 Pro 费用（一次性约 $50-100，含订阅选项）与 Photon 相比微不足道。
  • 构建自定义预测系统的最佳选择 on top of Ares.

1.3 Unity Netcode for GameObjects（NGO）

  • Stars: 2,311 | License: MIT / Unity Companion License | Backed by: Unity Technologies
  • Architecture: Unity 第一方解决方案。Client-Server 模型，使用 NetworkBehaviour, NetworkVariable, ServerRpc/ClientRpc。v2 增加了"分布式权威"（无需中心服务器的客户端托管对象）。
  • Sync Model: State Sync — NetworkVariable 复制、RPC。没有内置 Lockstep 或帧同步支持。没有内置客户端预测（必须自行编写）。
  • Dedicated Server: 支持 headless 构建。集成 Unity Multiplay Hosting 服务。
  • Rust/Ares 集成：⭐⭐⭐（可用）
  • NGO 默认使用 Unity Transport Package（UTP），与 Unity 的中继和托管服务紧密耦合。
  • 虽然可以编写自定义 NetworkTransport 实现，但 NGO 的架构对外部后端不如 Mirror/FishNet 友好。
  • Unity 生态系统锁定（UTP、Relay、Lobby、Multiplay）意味着连接到自定义 Rust 后端时会有更多摩擦。
  • 功能延迟：预测与和解不在路线图上；Unity 专注于"托管服务"生态系统。
  • Verdict: 仅在你致力于 Unity 完整多人游戏生态系统（Game Server Hosting、Relay、Matchmaker）时选择 NGO。不推荐用于自定义 Rust 后端。

1.4 Photon Fusion

  • Architecture: 基于 tick 的状态同步，内置预测和插值。服务器运行在 Photon Cloud（托管服务）或自托管 Photon Server。
  • Sync Model: State Sync with Prediction. Every NetworkObject has a NetworkTransform with prediction。使用固定 tick 频率（模拟以固定时间步长运行）。输入发送到服务器，服务器模拟，状态返回，客户端进行和解。
  • Protocol: 专有二进制协议。不支持 Protobuf。不支持自定义协议。
  • Rust/Ares 集成：❌（不可能）
  • PHOTON FUSION 无法连接到自定义服务器。 服务器必须是 Photon 的服务器插件或 Photon Cloud。它端到端使用 Photon 的专有二进制协议。
  • 没有传输抽象层——Fusion 是一个封闭系统（客户端和服务端都运行 Photon）。
  • 理论上可以在「Host Mode」下运行 Fusion（一个客户端作为服务器），但这违背了 Ares 的初衷。
  • Verdict: 不可行。如果你想用 Photon，就必须用 Photon Server——无法替换为 Ares。

1.5 Photon Quantum

  • Architecture: 确定性 Lockstep (Frame Sync). 整个模拟在完全确定性的自定义 ECS（Entity Component System）中运行。只传输玩家输入。服务器（Photon Cloud）运行与所有客户端相同的模拟——通过运行相同的确定性模拟，所有人达成状态一致。
  • Sync Model: Lockstep (Frame Sync). 这是唯一原生支持 Lockstep/帧同步的 Unity 网络代码。所有游戏逻辑在确定性 ECS 中运行（非 Unity GameObject）。物理、寻路等是确定性子系统。
  • Protocol: 专有协议。仅通过 UDP 传输玩家输入数据包。
  • Rust/Ares 集成：❌（不可能）
  • QUANTUM 无法使用外部服务器。 确定性 ECS 在所有地方运行（客户端 + Photon 服务器）。无法替换服务器——它已嵌入架构。
  • 自定义 ECS 也导致无法与 Ares 共享协议定义。
  • Verdict: 架构值得研究（带预测/回滚的确定性 Lockstep），但无法与 Ares 集成。可作为在 Unity 上实现自己的确定性 Lockstep 客户端的设计参考。

2. Unreal Engine 多人游戏分析

2.1 UE 内置网络架构

  • Model: 权威 Client-Server。服务器拥有所有游戏状态。客户端是渲染服务器状态的"哑终端"。
  • Replication System: UE 的复制系统深度集成到引擎中：
  • UPROPERTY(Replicated) — automatic property replication
  • RPCs (Server, Client, NetMulticast) — remote procedure calls
  • AActor::bReplicates — per-actor replication control
  • Replication Graph——大型世界的空间优化（网络剔除）
  • 预测与插值：
  • Client-side Prediction: Built into UCharacterMovementComponent 中。当客户端移动时，它在本地预测并将输入发送到服务器。服务器模拟移动，发送修正。UE 的 APlayerController and UCharacterMovementComponent 为角色移动自动处理预测/和解。
  • Interpolation: UE 在接收到的状态之间进行插值以实现平滑渲染。使用数据包时间戳和固定更新间隔。
  • Lag Compensation: Built-in via bAllowLagCompensation 内置。在验证 hitscan 武器时，服务器将命中目标回溯到客户端感知的位置。
  • Network relevancy: 内置空间相关性系统——服务器仅复制客户端附近的 Actor（等效于 AOI）。
  • 专用服务器工作流：
  • UE 编译专用服务器二进制文件（-server target platform)
  • Linux headless，无渲染依赖
  • 经大规模实战验证（Fortnite、Valorant 使用 UE 专用服务器）
  • 一流的 Docker/容器支持
  • Epic 的后端服务（EOS）可选但通常配套使用

2.2 UE + Rust/Ares 集成

可行性：⭐⭐（有挑战但可行）

UE's networking is 深度嵌入引擎。与 Unity 中网络代码是可以替换的独立包不同，UE 的复制涉及 AActor, UObject, UActorChannel, UNetDriver——这些核心引擎系统。

集成方案：

方案 A：替换 UNetDriver（非常困难） - UE's UNetDriver 处理所有网络 I/O、复制和 RPC 传递。 - 你需要编写一个自定义 UNetDriver 子类，发送/接收 Ares Protobuf 消息，而不是 UE 的内置二进制序列化。 - 这是一个巨大的工程——NetDriver 接口复杂、文档不足，且在不同 UE 版本间会变化。 - 你会失去 UE 的内置属性复制、RPC 系统和客户端预测，除非你重新实现它们。 - 不推荐。

方案 B：网关层（实用方案） - Keep UE's built-in networking disabled （无复制、无 NetDriver）。 - 在 UE 中使用 FUdpSocketBuilder 或 FTcpSocketBuilder 编写 C++ 网络层，通过 TCP 直接连接到 Ares Gateway。 - 在 UE 中实现自己的轻量级复制/预测系统，镜像 Ares 的 Protobuf 消息。 - 将 UE 仅作为 渲染和输入引擎——所有游戏状态来自 Ares。 - 这本质上是构建一个"瘦客户端"——你失去了 UE 的内置网络功能，但获得了完全控制权。 - 仍然需要大量的 C++ 专业知识和深入理解 UE 的游戏循环。

方案 C：EOS P2P 桥接（取巧方案） - 使用 Epic Online Services（EOS）P2P 作为传输桥接。 - 不优雅——添加了不必要的层次和 EOS 依赖。

关键挑战： - UE 的复制系统不是设计为可"替换"的。它是引擎的结构性组成部分。 - UE 的 C++ 编译时间在迭代期间很慢。 - UE 的角色移动系统与其网络模型紧密耦合——提取出来用于 Ares 需要大量工作。 - Unity 的方法（写一个 Transport，替换进去）在 UE 中没有干净的等价方案。

2.3 UE 内置 Lockstep/帧同步

  • UE has no built-in Lockstep 或 deterministic frame sync support.
  • UE 的物理引擎（PhysX/Chaos） not deterministic. 在 UE 中构建 Lockstep 游戏需要将物理引擎替换为确定性引擎，这极其困难。
  • UE 中的 RTS/MOBA 游戏通常在游戏逻辑层（而非引擎层）使用状态同步 + lockstep——例如自定义确定性游戏状态类。

核心洞察：Transport 抽象层的优势

Unity 在网络代码逻辑和实际网络 I/O 之间有一个「传输」层。你可以编写一个 MonoBehaviour 实现： 1. Receives ArraySegment<byte> 2. 将其包装为 Ares Protobuf 消息 3. 通过 TCP 发送到 Ares Gateway 4. 接收 Ares Protobuf 消息 5. 将原始字节传回到网络代码

This is 大约 200 行 C# 代码。 Mirror 有明确的 Transport 文档；FishNet 有类似文档。网络代码处理其他一切（RPC 分发、对象生命周期、场景管理）。

Unreal Engine 没有等效的抽象点。你要么： - 使用 UE 的完整网络栈（服务器权威复制）——无法使用 Ares - 完全绕过 UE 网络并自己构建——失去所有引擎优势 - 编写自定义 NetDriver（巨大工程，文档不足）

5. 实践建议

5.1 Engine Recommendation: Unity + FishNet (or Mirror)

对于在 Ares 上构建自定义客户端框架，Unity + Mirror 或 FishNet 是明显的赢家。

理由： 1. Transport 抽象是杀手级特性。 你只需写约 200 行 C# 即可将网络代码桥接到 Ares。无需修改引擎。 2. Iteration speed is critical 构建自定义客户端框架时——Unity 的快速编译时间和播放模式是巨大优势。 3. FishNet's prediction system 是构建 Ares 客户端框架的最佳参考实现。你可以直接使用或作为参考研究。 4. C# 人才比 C++ UE 开发者更丰富且成本更低。 对于重网络的项目招聘更快。 5. 你掌控整个网络栈。 Unity netcode + 自定义 Transport + Ares = 清晰的分层架构。 6. Mirror 是 MIT 许可证——零成本、零风险。 FishNet's Pro is $50-100 one-time.

Mirror vs FishNet： - If you need built-in prediction/reconciliation now: FishNet - If you want 零成本、MIT 许可证、经过大规模验证 （1 亿+ 玩家）：Mirror - If you plan to build custom prediction ：Mirror（代码库更简单易懂） - If you want 最先进的功能集: FishNet

5.2 推荐架构

Unity Client
├── AresClientTransport (custom Mirror/FishNet Transport)
│   ├── TCP Socket → Ares Gateway
│   ├── Protobuf Serialization/Deserialization
│   └── Message Routing by MsgCategory
├── AresClientFramework (custom layer)
│   ├── Lockstep Mode: Input gathering → Send to Ares → Receive FrameData → Execute
│   ├── StateSync Mode: Receive StateUpdates → Apply with AOI → Render with interpolation
│   ├── Hybrid Mode: Lockstep + periodic StateSync validation
│   └── Prediction/Reconciliation (FishNet or custom)
├── Game Logic Layer (genre-specific)
│   ├── MOBA: Hero movement, ability system, fog of war
│   ├── FPS: Weapon system, hit registration, recoil
│   └── Action: Combo system, animation state machine
└── Unity Rendering & Input

5.3 何时选择 Unreal Engine

仅在选择以下条件时选择 UE： - You need AAA-level graphics 开箱即用（Nanite、Lumen、Niagara） - You're building a first-person shooter ，UE 的内置角色移动/预测可以节省大量开发时间（但需注意：你需要将其移植以适配 Ares） - 你的团队已有 strong C++ UE engineers 已有 - You're willing to spend significantly more engineering time on network integration

5.4 开发路线图

  1. Week 1-2: 研究 Ares Protobuf 定义和 Gateway 协议
  2. Week 3-4: Build AresClientTransport 为 Mirror 构建 AresClientTransport（实现 Transport 抽象类）
  3. Week 5-6: 实现基础 Lockstep 客户端（输入 → Ares → FrameData → 执行）
  4. Week 7-8: 添加 StateSync 客户端（接收状态更新，结合 AOI 应用）
  5. Week 9-10: Implement prediction and reconciliation
  6. Week 11-12: 在上层构建特定类型的游戏逻辑
  7. Ongoing: 使用现有 stress-bot 基础设施进行压力测试
