游戏服务器架构方法论

语言是工具，架构是思想。本文档提炼 Ares 项目中可迁移到任何语言（C++/Go/Java）的通用设计方法论。

一、核心原则

1.1 协议先行

不管你用什么语言，第一步永远是定义消息。

错误的做法：先写 Gateway 代码，边写边加字段
正确的做法：先写 .proto，所有服务基于同一份契约开发

Ares 的做法：6 个 proto 文件（common/gateway/game/room/battle/chat），所有服务共享 ares-common crate。换成 C++ 就是同一个 protobuf 生成的 .pb.h/.pb.cc，所有服务链接同一个库。

面试时这样说：

"我们采用协议先行（Contract-First）的开发模式。所有服务间通信基于 protobuf 定义，服务端和客户端 SDK 从同一份 proto 生成代码。这保证了——不管后端用什么语言重写、不管客户端是 Unity 还是 UE，契约不会变。"

1.2 分层解耦

游戏服务器的分层是通用的，与语言无关：

┌─────────────────────────────────────┐
│           Client (Unity/UE)         │  ← 表现层
├─────────────────────────────────────┤
│   Gateway（TCP 接入 / 消息路由）      │  ← 接入层
├──────────┬──────────┬───────────────┤
│   Game   │   Room   │    Chat       │  ← 业务层
│ (Auth/   │ (房间/   │  (聊天/       │
│  Match)  │  分配)   │   社交)       │
├──────────┴──────────┴───────────────┤
│          Battle（战斗引擎）           │  ← 计算层
├─────────────────────────────────────┤
│   etcd / MySQL / Redis / Docker     │  ← 基础设施层
└─────────────────────────────────────┘

每一层关心的事情不同，对语言的要求也不同：

层 核心关注点 C++ 实现 Rust 实现
接入层 高并发连接、低延迟转发 epoll + libuv / boost.asio Tokio TCP
业务层 逻辑正确性、状态管理 Actor 模式 / 状态机 Arc<RwLock<>>
计算层 CPU 密集型（模拟/物理） 线程池 + SIMD Rayon / 裸线程
基础设施 可靠性、一致性 etcd-cpp-apiv3 etcd-client

面试时这样说：

"分层设计的本质是隔离变化。Gateway 不关心匹配算法怎么实现，Battle 不关心玩家从哪个 Gateway 接入。每一层可以独立扩缩容、独立用不同语言重写。"

1.3 为失败设计

任何服务调用都可能失败，这是分布式系统的第一定律。

Ares 目前做得好的：心跳检测 + 超时踢出 Ares 还没做的（但方法论上必须有）：

  • 熔断：某个后端连续失败 N 次 → 暂时不再请求它
  • 重试：指数退避 + jitter（防止惊群）
  • 降级：etcd 不可用时，fallback 到静态配置
  • 幂等：同一个匹配请求不能重复处理

面试时这样说：

"我们为每个 gRPC 调用设置了超时和重试策略。对于匹配这种关键路径，我们用 etcd 的 CAS 操作保证幂等——即使重试，同一个玩家不会被匹配两次。对于非关键路径如聊天，允许短暂失败。"

二、设计方法论：拿到需求怎么下手？

2.1 数据流优先

不要上来就写代码。先画数据流图。

以 Ares 的「匹配 → 进入战斗」为例：

Player ──TCP──▶ Gateway ──gRPC──▶ Game/MatchEngine
                                       │
                                 匹配成功？
                                       │
                    ┌──────────────────┘
                    ▼
              RoomManager.create_room()
                    │
                    ▼
              Battle 节点分配（LeastLoaded）
                    │
                    ▼
              BattleServer.create_battle()
                    │
                    ▼
              返回 battle_addr + join_token
                    │
                    ▼
              Client 直连 BattleServer（UDP/WebSocket）

画完数据流后，自然就能回答： - 哪些调用是同步的？哪些可以异步？ - 每个环节失败怎么办？ - 瓶颈在哪里？

2.2 状态边界清晰化

每个服务有自己的状态域，不要越界：

服务 拥有的状态 不拥有的状态
Gateway 连接 session、心跳时间 玩家 MMR、房间信息
Game 玩家在线状态、匹配池 战斗帧数据
Room 房间列表、Battle 分配 战斗逻辑
Battle 战斗实例、帧数据、录像 玩家账号信息

面试时这样说：

"我们把状态严格限定在所属服务内。比如 Battle 挂了，只影响当前战斗——玩家可以立刻重新匹配。如果所有状态都放在一个单体里，一个模块挂了整个游戏就停了。"

2.3 一致性模型分级

不是所有场景都需要强一致性：

强一致性（CP）         最终一致性             可用性优先（AP）
──────────────────────────────────────────────────────
匹配结果（不能重复）    房间状态变更通知         Gateway 路由
战斗帧顺序              玩家在线状态             聊天消息
MMR 结算                排行榜更新              心跳

面试时这样说：

"匹配引擎用 etcd 的原子操作保证不会重复匹配——这是 CP。Gateway 的路由表通过 watch etcd 更新，允许短暂不一致——这是 AP。不同场景选不同的一致性模型，这是分布式系统设计的核心 trade-off。"

三、与语言无关的核心技术领域

以下每个领域，Ares 已经有 Rust 实现。你需要在方法论层面理解它们，能换成 C++ 描述。

3.1 网络模型

概念 Rust（Ares） C++ 等价
异步 TCP tokio::net::TcpListener boost::asio::ip::tcp::acceptor + io_context
消息编解码 tokio_util::codec::Framed 自定义 length-prefix codec
gRPC 客户端 tonic grpc++（protobuf 官方）
广播通道 tokio::sync::broadcast 手写 subscriber list + mutex

核心理解： 不管什么语言，网络模型都是「事件循环 + 非阻塞 IO」。Rust 的 Tokio、C++ 的 Boost.Asio、Go 的 goroutine——底层都是 epoll/kqueue。

3.2 并发模型

模式 适用场景 Ares 中用在哪
Arc<RwLock<T>> 读多写少 RoomManager, BattleManager
tokio::mpsc channel 消息驱动 Gateway session → 写 half
AtomicU64 无锁计数 连接数、请求数统计
parking_lot::RwLock 更快的读写锁 MatchEngine

C++ 等价： std::shared_mutex, std::atomic, boost::lockfree::queue

3.3 战斗同步模式

这是 Ares 的核心竞争力。三种同步模式与语言完全无关：

模式 服务器做什么 客户端做什么 适用游戏
Lockstep 收集输入 → 广播 确定性执行 RTS、格斗、MOBA
StateSync 执行逻辑 → 广播状态 预测 + 插值 FPS、MMO
Hybrid Lockstep 为主 + 服务器抽查 正常 Lockstep 竞技型

面试时这样说（C++ 面试官也能听懂）：

"我实现了三种同步模式。Lockstep 的核心是一个 InputBuffer——客户端提前 N 帧发输入，服务器按帧收集后广播。这跟语言无关，核心是一个 HashMap>。换成 C++ 就是 std::unordered_map>。"

3.4 匹配算法

Ares 的匹配引擎是完全语言无关的纯算法：

1. 按 MMR 分桶（mmr / 100 * 100）
2. 每 2 秒一轮撮合
3. ELO 范围逐轮扩大：±50 → ±75 → ±100 → ... → ±300
4. ABBA 分边保证公平

C++ 等价： std::map<uint32_t, std::deque<MatchRequest>>

四、重构后的学习计划

把「学 Rust」替换为「学分布式系统设计模式」，语言只是验证工具。

阶段一：分布式系统核心模式（2 周）

不再学「Rust 怎么用 etcd」，而是学「服务发现的设计模式」：

  • 注册模式：Self-Registration vs Third-Party Registration
  • 发现模式：Client-Side Discovery vs Server-Side Discovery
  • 健康检查：Push（心跳）vs Pull（健康端点）
  • 用 etcd 在 Ares 中落地（语言无关，换成 ZooKeeper/Consul 同理）

阶段二：数据架构模式（2 周）

  • CQRS：命令查询职责分离
  • Event Sourcing：事件溯源
  • 缓存策略：Cache-Aside / Write-Through / Write-Behind
  • 分库分表：垂直拆分 vs 水平拆分
  • 在 Ares 中选择合适的策略落地

阶段三：容错与弹性模式（2 周）

  • Circuit Breaker（熔断器）
  • Bulkhead（舱壁隔离）
  • Retry + Backoff + Jitter
  • Timeout 层级设置
  • 优雅降级

阶段四：可观测性（2 周）

  • 三大支柱：Logging / Metrics / Tracing
  • 结构化日志的设计原则
  • RED 方法论（Rate / Error / Duration）
  • Prometheus + Grafana 落地

阶段五：系统设计面试（4 周）

  • 白板画架构图
  • 容量估算（QPS、带宽、存储）
  • Trade-off 分析
  • 模拟面试

五、面试时的叙事框架

30 秒版本：

"我做了一个分布式游戏服务器框架，核心是分层架构 + 三种战斗同步模式。技术栈是 Rust，但设计方法论是语言无关的——换成 C++ 就是换套标准库的事。"

5 分钟深度版（按这个结构讲）： 1. 协议先行：6 个 proto，客户端和服务端共享契约 2. 分层解耦：Gateway / Game / Room / Battle / Chat 各司其职 3. 战斗引擎：三种同步模式的 trade-off 分析 4. 匹配系统：ELO + 逐轮放宽 + ABBA 分边 5. 分布式设计：etcd 服务发现 / CAP 权衡 / 故障处理

被问「Rust 项目投 C++ 岗位？」时的回答：

"Ares 虽然用 Rust 写的，但它的架构设计——分层解耦、协议先行、同步模式——跟语言完全无关。我选 Rust 是因为它强制我思考内存安全和并发安全，这些思考在 C++ 里同样适用。实际上，Ares 里的每个组件我都能用 C++ 重新描述一遍实现方案。"
