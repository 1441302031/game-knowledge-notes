Q1：CPU 缓存是如何影响游戏性能的？你怎么优化？

⚡ 30 秒版（电梯演讲，一句话说清楚）

CPU 缓存是离 CPU 最近的存储器，访问延迟约 1ns，而主存约 100ns。游戏性能优化的核心就是把热数据尽可能留在缓存里——用连续数组代替链表、行优先遍历代替列优先遍历、把同一帧内一起访问的数据放在相邻内存位置。

🕐 3 分钟版（标准面试回答）

第一步：讲清楚缓存层次结构（30秒）

现代 CPU 有三级缓存。L1 最小（32KB）但最快（~1ns），L2 稍大（256KB，~4ns），L3 最大（8-32MB，~12ns），主存 ~100ns。每一级缓存的命中率都对性能有指数级影响。

第二步：讲清楚为什么影响游戏性能（1分钟）

游戏每帧都要处理大量数据——Transform 矩阵、顶点数据、物理碰撞。如果这些数据分散在内存各处，CPU 频繁 Cache Miss，每次 Miss 都要等 100+ 周期。一帧 16.6ms，在现代 4GHz CPU 上约 6600 万周期，每 1000 次 Cache Miss 就是 10 万周期——这很快就吃掉你的帧预算。

ECS（Entity Component System）架构的快，不是因为"去掉了继承"，而是因为 Component 被紧凑排列在连续内存中，CPU 预取一整条 Cache Line（64 字节），后续 63 字节的访问都命中缓存。

第三步：讲具体优化手段（30秒）

三个原则： 1. 空间局部性：热数据放一起。比如用 struct Position { float x, y, z; } 的数组，而不是每个对象分散存储 2. 时间局部性：频繁访问的数据不要让它被换出。对象池就是这个目的 3. 避免伪共享：多线程场景下，两个线程写同一 Cache Line 的不同变量，会导致缓存一致协议（MESI）频繁失效

（接 3 分钟版后，追加以下内容）

1. 用 Benchmark 数据说话

举个矩阵乘法的例子。1024×1024 矩阵乘法，行优先遍历 vs 列优先遍历：

行优先：每次内层循环访问的是同一行，空间局部性好 → Cache Miss 率 ~0.5%
列优先：每次内层循环访问的是不同行的同一列 → Cache Miss 率 ~50%
性能差距：5-10 倍

我在自己的项目中遇到过类似问题——游戏服务器做帧同步时，需要遍历所有玩家的输入。最早用 HashMap<PlayerId, Input> 存储，每次遍历都是随机内存访问。改为 Vec<Input> 顺序存储后，遍历速度提升了 3 倍。

2. 伪共享的真实案例

两个线程分别更新数组中相邻的两个计数器：

Thread 1: counters[0]++
Thread 2: counters[1]++

这两个计数器在同一 Cache Line（64 字节）上。线程 1 写入时，该 Cache Line 被标记为 Modified，线程 2 的缓存中该 Line 失效，必须从内存/其他缓存重新加载——即使它们操作的是完全不同的变量。这就是伪共享。

解法：在计数器之间加 Padding，确保每个计数器独占一个 Cache Line：

struct PaddedCounter {
    int value;
    char padding[60]; // 64 - sizeof(int) = 60
};

3. 在游戏引擎中的实践

Unity DOTS 的 ECS 架构就是缓存优化的集大成者： - Entity 只是 ID，不存数据 - Component 按类型连续存储（NativeArray<ComponentType>） - System 批量处理同类型 Component → 最大化缓存命中 - Burst Compiler 在此基础上做自动 SIMD 向量化

对比传统 GameObject：每个对象散落在堆中，遍历一千个对象可能产生上千次 Cache Miss。

🔬 深入版（碾压所有追问）

追问 1："Cache Miss 有几种类型？怎么区分？"

三种（"3C 模型"）： - Compulsory Miss（冷启动 Miss）：第一次访问数据，必然不命中。只能通过 Prefetching 缓解 - Capacity Miss（容量 Miss）：工作集大于缓存容量。解决方案：减小工作集（数据压缩、精度降低） - Conflict Miss（冲突 Miss）：多个地址映射到同一 Cache Set。解决方案：改变数据布局避免冲突

追问 2："缓存一致性协议 MESI 怎么工作？"

MESI 有四个状态： - Modified：该 Cache Line 只在当前核心，且已被修改，与主存不一致 - Exclusive：只在当前核心，但内容与主存一致 - Shared：可能在多个核心，内容与主存一致 - Invalid：该 Cache Line 无效

当一个核心写入时，需要通过总线广播使其他核心的对应 Line 变为 Invalid。这就是为什么多线程写入同一 Cache Line 代价极大。

追问 3："怎么用 perf 看 Cache Miss？"

perf stat -e cache-references,cache-misses ./your_program
perf record -e cache-misses ./your_program
perf report

Cache Miss 率超过 3-5% 就值得关注了。用 perf annotate 可以精确到指令级。

追问 4："Prefetching 是什么？什么时候用？"

现代 CPU 有硬件预取器（Hardware Prefetcher），会自动把顺序访问的数据预取到缓存。但当访问模式不规则时，需要软件预取：

__builtin_prefetch(&data[next_index], 0, 3); // GCC 内置预取

在遍历链表、跳表等场景中，提前预取下一个节点可以大幅度减少延迟。

Q2：Draw Call 是什么？为什么多了会卡？怎么优化？

⚡ 30 秒版

Draw Call 是 CPU 向 GPU 下达的一次"画东西"的指令。它的开销主要在 CPU 端——每次 Draw Call 都要做状态切换（换 Shader、换纹理、换混合模式），这些切换本身比 GPU 画几个三角形还耗时。优化核心是"合批"——让多个物体共用一次状态切换。

🕐 3 分钟版

第一步：GPU 渲染管线（30秒）

想象 CPU 和 GPU 之间有座桥。CPU 通过 Driver 把"画什么、用什么画"的指令打包成 Command Buffer，GPU 从桥另一边取走执行。一次 Draw Call = CPU 打包一次。

第二步：开销分析（1分钟）

问题不在 GPU 画的过程——GPU 画 100 个三角形分 100 次和 1 次，耗时差不多。问题在 CPU 打包的过程： 1. 状态验证：当前 Shader 变了吗？纹理变了吗？渲染状态变了吗？ 2. 资源绑定：把新的纹理、Buffer 绑定到 GPU 管线 3. API 调用开销：每个 glDrawElements / DrawIndexed 本身就是一次函数调用

在移动端这个问题更严重——TBR（Tile-Based Rendering）架构下，每次状态切换还可能触发 Tile 的 flush。

第三步：核心优化策略（1分钟）

策略 原理 Unity 对应
静态合批 预先合并网格，多个物体 = 1 个 Draw Call Static Batching
动态合批 运行时合并顶点（限小网格，顶点<300） Dynamic Batching
GPU Instancing 同一个网格、同一个材质，用实例数据区分 DrawMeshInstanced
SRP Batcher 缓存材质属性，仅更新变化部分 需 URP/HDRP
纹理 Atlas 多个小纹理合并为一张大图 Sprite Atlas

📊 10 分钟版

（接 3 分钟版，追加以下内容）

1. Unity Frame Debugger 实战

一个典型的 UI 界面优化过程： - 优化前：200+ Draw Call，Frame Debugger 显示"每次都是 SetPass Call（Shader 切换）" - 发现问题：20 种字体用了 15 种不同材质 - 解决方案：统一字体材质 → 开 Sprite Atlas → Draw Call 降到 18 - 帧时间从 22ms 降到 11ms

2. 现代 API 如何解决（Vulkan/DX12/Metal）

传统 OpenGL/DX11 的痛点：每次状态切换都是隐式的，驱动替你管理，但管理本身有开销。

现代 API 的核心改进： - Pipeline State Object (PSO)：提前把所有渲染状态"烘焙"成一个不可变对象，运行时只需一次绑定 - Command Buffer 可重用：录制一次，多次提交 - Indirect Draw：让 GPU 自己决定 Draw Call 参数，CPU 不需要挨个指定

这就是为什么 DOTS + URP 可以有巨大的 Draw Call 优势——底层就是把这些机制串起来了。

3. 一个"看似聪明实则没用"的陷阱

有人想：我把 100 个不同材质的物体逐个合并到一个大 Mesh，不就成了 1 个 Draw Call？

问题：合并后的大 Mesh 只有一个材质槽。你得把这 100 种材质"烘焙"到一张大纹理上。每次加新物体都要重新烘焙，工作流爆炸。这就是"Overdraw 不是唯一指标"的原因。

🔬 深入版

追问 1："SetPass Call 和 Draw Call 有什么区别？"

  • Draw Call：每次 DrawIndexed 调用。同一个 Shader 内，切换纹理也会产生新 Draw Call
  • SetPass Call：切换 Shader/Pass。开销远大于 Draw Call

Unity Stats 面板中，通常"Batches = Draw Call"，"SetPass calls ≈ Shader 切换次数"。优先减少 SetPass Call。

追问 2："TBR 架构和 IMR 架构的差异？"

  • IMR（Immediate Mode Rendering，桌面端）：立即渲染，三角形逐个画到 Frame Buffer。状态切换代价在于绑定点变更
  • TBR（Tile-Based Rendering，移动端）：GPU 把屏幕分为 N×M 像素的 Tile。每个 Tile 有自己的片上缓存，全部三角形排序后按 Tile 渲染。切换 Render Target/Shader 可能触发当前 Tile 的全部 Flush + 重新加载

移动端优化特别要注意： - 尽量不要在帧中间切换 Render Target - 减少 Shader 变体 - 用 ASTC 纹理压缩（硬件原生支持）

追问 3："GPU Instancing 的底层怎么实现？"

GPU Instancing 使用 SV_InstanceID 这个系统值。在 Shader 中，可以基于 InstanceID 从 Instance Buffer 中取每实例数据（每个物体的 Transform、颜色等）。GPU 硬件层面，多个实例共享同一组 Shader 代码和状态，仅 Instance Buffer 偏移不同。

但限制是：同一 Mesh + 同一 Material。因为不同 Material 意味着不同的 Shader/纹理——那又回到了状态切换问题。

Q3：帧同步和状态同步有什么区别？你项目中用的哪种？

⚡ 30 秒版

帧同步是"同步输入"——所有客户端跑同一个逻辑序列，只传玩家操作，适合 RTS/MOBA。状态同步是"同步结果"——服务器算权威结果，广播给客户端插值，适合 FPS/MMO。前者带宽低但确定性要求高，后者带宽高但延迟容忍性好。

🕐 3 分钟版

第一步：讲清楚原理差异（1分钟）

维度 帧同步（Lockstep） 状态同步（Snapshot）
同步什么 玩家输入（操作指令） 游戏状态（位置、血量、技能CD...）
谁算逻辑 所有客户端独立计算 服务器算，客户端插值
带宽 极低（几 KB/s） 较高（几十 KB/s）
延迟敏感度 高——一人慢，全员等 低——客户端预测弥补
确定性要求 极高——浮点数必须一致 无——服务器是唯一真相
代表游戏 王者荣耀、星际争霸 CS:GO、PUBG、魔兽世界

第二步：关键 Trade-off（30秒）

帧同步的最大优势是带宽——MOBA 类游戏 10 个玩家，只需传 10 份输入。但代价是确定性：同一帧、同一输入，不同设备必须算出完全相同的状态。浮点数在不同平台（x86 vs ARM）可能不同，这是个巨大的工程挑战。

状态同步反过来——延迟用"客户端预测 + 服务器和解"解决，但每帧要同步大量状态。

第三步：结合你的项目（1分钟）

在 Ares 项目中，我们选了帧同步。核心设计： - Gateway 负责连接管理，Game Service 跑帧逻辑 - Battle Service 管理确定性模拟 - 使用 Fixed Timestep 保证每帧逻辑一致 - 压测结果：100 连接，零超时零错误，吞吐 3,485 RPS，平均延迟 28.68ms

（接 3 分钟版，追加以下内容）

1. 帧同步的确定性怎么保证？

帧同步的确定性是"最坑"的地方。几个关键问题：

  1. 浮点数：x86 用 80 位扩展精度，ARM 是 64 位。解法：全部转为 32 位定点数或使用 _controlfp 控制精度。更彻底的方案是用定点数学库。
  2. 随机数：必须用同一个种子 + 同一个算法。不能用系统 rand()，必须自己实现确定的随机数生成器（如 Xorshift）
  3. 执行顺序：事件处理的顺序必须一致。比如"先处理碰撞再处理技能" vs "先处理技能再处理碰撞"可能导致完全不同的结果
  4. 帧内逻辑：不能在帧逻辑中混入"当前真实时间"——必须用帧号作为时间基础

2. 乐观帧同步 vs 严格帧同步

  • 严格帧同步：每个客户端都要等到所有输入到齐才推进一帧。延迟 = 最慢玩家的延迟
  • 乐观帧同步（王者荣耀用的）：不等，先按预测执行；如果后来发现不一致，回滚重算

乐观帧的复杂度远高于严格帧，但用户体验好得多。

3. 状态同步中延迟补偿怎么做的？（CS:GO 案例）

当你（客户端 A）射击敌人（客户端 B），你的子弹判定发生在你的本地时间 T。但服务器看到的是：在服务器时间 T，敌人 B 已经移动了 100ms。

Lag Compensation 的做法： 1. 服务器保存过去 1 秒内所有玩家的位置快照 2. 收到 A 的射击请求时，回退所有玩家到"射击发生时刻 (T - RTT/2)"的位置 3. 在回退的状态下做命中判定 4. 如果命中，服务器通知 B："你被击中了"，B 的客户端回滚显示击杀动画

4. 我在 Ares 项目中的额外优化

  • 使用 ProtoBuf 做增量同步：不是每帧发完整状态，而是发变化的部分——带宽从 15KB/s 降到 3KB/s
  • 独立进程架构：Gateway/Game/Room/Battle 各自独立进程，通过 gRPC 异步通信，避免锁竞争
  • 帧同步 + 状态混合模式：对关键操作（如技能释放）用帧同步保证公平，对非关键表现（如粒子特效）用状态同步降低延迟感知

🔬 深入版

追问 1："浮点数在不同平台的一致性怎么保证？"

根本原因：x86 FPU 内部寄存器是 80 位（扩展双精度），写入内存时截断为 64 位。ARM 没有 80 位寄存器。同样的浮点运算，在不同平台因为中间精度不同而产生偏差。

解决方案（按推荐顺序）： 1. 定点数：用 64 位整数表示"毫单位"。坐标用 1/1000 精度，确定性 100% 2. 强制单精度：volatile float 强制每次操作后写入内存（截断），但性能损失 3. -ffloat-store：GCC 编译选项，强制截断，但仅限 x86 4. Software Float：纯软件实现 IEEE 754，跨平台一致但慢

追问 2："帧同步怎么处理断线重连？"

断线玩家重新加入时，需要"追赶"到当前帧。两种方案： 1. 全状态快照：服务器定时保存完整状态快照，重连时从最近快照 + 重放输入。占用存储 2. 从头重算：从第 0 帧开始重算到当前帧。需要保存所有历史输入。CPU 开销大但存储小

我们在 Ares 中用快照方案：每 60 帧（1 秒）保存一次快照，重连时从快照 + 最多 59 帧重放。

追问 3："为什么状态同步的 MOBA 很少见？"

MOBA 10 人 + 大量小兵 + 技能弹道，全状态同步的带宽不可接受。每帧每个单位的 3D 坐标+状态可能 50+ 字节，10 人 × 100+ 单位 = 5000+ 字节/帧 × 60fps = 300KB/s——远超手游 3G/4G 带宽上限。

帧同步只需传 10 个人的操作，每个操作几个字节，总计 < 5KB/s。

Q4：Unity 中的 GC 如何影响性能？怎么优化？

⚡ 30 秒版

GC（垃圾回收）会在主线程上暂停所有代码执行来回收内存。在 60fps 下每帧只有 16.6ms，一次 Gen2 GC 可能吃掉 5-15ms，直接导致卡顿。优化核心是"不产生垃圾"——用 struct 代替 class、对象池、StringBuilder 复用、避免 Update 中分配新对象。

🕐 3 分钟版

第一步：Unity GC 的分代机制（30秒）

Unity 用的是 Boehm GC（IL2CPP 模式下类似），分两代： - Gen 0：新分配的小对象，快速回收（~1ms） - Gen 1/2：存活时间长的对象，回收时扫描整个堆（~5-15ms），这会阻塞主线程

第二步：什么时候触发 GC？

  1. Gen 0 满了（通常几 KB 到几十 KB 就触发）
  2. 手动调用 System.GC.Collect()
  3. 加载新场景时
  4. 堆分配量的累积——即使你主动不触发 GC，分配量超过阈值也会自动触发

第三步：核心优化策略（1分钟）

  1. 值类型优先：struct 在栈上分配，不走 GC。坐标、颜色、小数据结构全部用 struct
  2. 对象池：GameObject/自定义 class 实例复用，不要频繁 Instantiate/Destroy
  3. 字符串：字符串是不可变的，每次拼接都产生新对象。用 StringBuilder 或用 string.Format
  4. 容器预分配：new List<T>(capacity) 而不是 new List<T>()，避免动态扩容
  5. 避免装箱：int 转 object 会在堆上分配。UI 回调中的闭包也是隐形 GC 来源
  6. 避免每帧分配：Update 中 new 任何东西都是罪过

📊 10 分钟版

（接 3 分钟版）

1. 一个优化的真实案例

一个 UI 界面，每帧都在 Update 中做：

void Update() {
    label.text = "Score: " + score; // 字符串拼接 = GC Alloc
    var pos = transform.position;     // Vector3 = struct，没问题
    var list = new List<Enemy>();     // 每帧 new = GC 地狱
    list.AddRange(FindObjectsOfType<Enemy>()); // 又一个 new
}

Profiler Deep Profile 显示：Update 每帧产生 2.3KB GC Alloc。60fps × 2.3KB = 138KB/s，Gen 0 每 2-3 帧就满。优化后：

void Update() {
    label.text = scoreText;  // 预先缓存的字符串
    enemyList.Clear();       // 复用容器
    GetEnemiesNonAlloc(enemyList); // 非分配版本
}

GC Alloc 降到 0 字节。

2. Profiler 怎么看 GC？

Unity Profiler → CPU Usage → 找黄色的 "GC.Collect" 标记。展开看 "GC Alloc" 列，按每帧排序，红色标记的就是问题函数。Deep Profile 模式可以精确到行。

3. IL2CPP 模式下 GC 有不同吗？

IL2CPP 用的也是类似 Boehm GC 的保守 GC。没有"真正的分代"，但分配策略更激进。好处是 IL2CPP 下代码执行更快，坏处是 GC 停顿可能比 Mono 更长。

🔬 深入版

追问 1："struct 和 class 怎么选？"

三个原则： 1. 数据小（< 16 字节）→ struct：复制开销小，栈分配，无 GC 2. 数据大、需要引用语义 → class：避免频繁复制大 struct 3. 需要继承 → class：struct 不支持继承（但可以实现接口）

陷阱：struct 里包含 class 引用（如 string），那它本身在栈上，但内部的引用指向堆。如果 struct 被 copy，两个 struct 指向同一个堆对象——这不是 bug，但要小心。

追问 2："对象池怎么设计？"

public class ObjectPool<T> where T : Component {
    Queue<T> pool = new Queue<T>();
    T prefab;

    public T Get() {
        if (pool.Count > 0) {
            var obj = pool.Dequeue();
            obj.gameObject.SetActive(true);
            return obj;
        }
        return Instantiate(prefab);
    }

    public void Return(T obj) {
        obj.gameObject.SetActive(false);
        pool.Enqueue(obj);
    }
}

重点： - 预分配一批（比如 20 个），避免运行时 Instantiate - Return 时重置状态（位置归零、血量重置） - 池满了要处理（扩容 or 销毁）

追问 3："值类型在泛型集合中会被装箱吗？"

List<int> —— 不会。.NET 泛型在编译时为每种值类型生成专门的代码（Reified Generics），所以 List<int> 内部存的是 int[]，不需要装箱。

但 List<object> 存 int 就会装箱。Dictionary<int, object> 中 key 不装箱，value 装箱。

Q5：多线程在游戏引擎中怎么用？有哪些坑？

⚡ 30 秒版

游戏的逻辑通常在主线程，但渲染、物理、音频、文件加载可以并行。现代引擎用 Job System 把任务拆成细粒度 Job 调度到工作线程。核心坑是三个：Race Condition（数据竞争）、伪共享（False Sharing）、上下文切换开销——多线程不一定快，但要串行化的部分决定了上限（阿姆达尔定律）。

🕐 3 分钟版

1. 游戏引擎的典型多线程架构（1分钟）

主线程      渲染线程      工作线程池      I/O线程
  │            │             │              │
  ├─ Update    │             │              ├─ 文件加载
  ├─ 提交渲染   ├─ 渲染命令    ├─ 寻路计算      ├─ 网络收发包
  ├─ 调度Job   │             ├─ 粒子更新      ├─ 资源解压
  │            │             ├─ 骨骼蒙皮      │
  ├─ 合并Job   │             ├─ 碰撞检测      │
  │            │             │              │
 16.6ms      渲染一帧       并行执行        异步完成

Unity DOTS 的 Job System 就是这个架构的体现。

2. 核心问题和解决方法（1分钟）

问题 表现 解法
Race Condition 两个线程同时写一个变量，结果不可预测 锁（Mutex）、原子操作、数据分片（每个线程只写自己的）
伪共享 两个线程写同一 Cache Line 的不同变量，性能暴跌 Padding 间隔
死锁 两个线程相互等待对方的锁 锁顺序一致、try_lock
上下文切换 线程太多，内核频繁切换 线程数 ≤ CPU 核心数

3. 阿姆达尔定律（Amdahl's Law）（30秒）

如果有 50% 的代码必须串行（如游戏逻辑依赖上一帧的结果），那么即使有无限核心，最大加速比也只有 2x。这就是"多线程不一定快"的根本原因。

📊 10 分钟版

（接 3 分钟版）

1. 锁的开销到底多大？

无竞争锁（uncontended）：一次 lock / mutex.lock() 约 20-30ns（原子操作开销）。 有竞争锁（contended）：等待时间 = 临界区执行时间 × 等待线程数。在线程多时，锁的持有时间会增加（因为上下文切换打断临界区）。

实测：4 个线程竞争一个锁，每个线程执行 100ns 的临界区 → 总吞吐不到单线程的 50%。

2. 原子操作 vs 锁

// 用锁
int counter = 0;
std::mutex mtx;
void increment_lock() {
    std::lock_guard<std::mutex> guard(mtx);
    counter++;  // 临界区只有一行，但锁的开销远大于++
}

// 用原子操作
std::atomic<int> counter(0);
void increment_atomic() {
    counter.fetch_add(1, std::memory_order_relaxed);
}

原子操作开销 ~5-10ns，锁 ~20-30ns + 可能的等待。

3. Amdahl 定律的实战计算

假设游戏每帧工作： - 80% 可以并行（渲染命令准备、粒子更新、寻路） - 20% 必须串行（逻辑更新、依赖链）

即使 16 核，最大加速比 = 1 / (0.2 + 0.8/16) = 1 / (0.2 + 0.05) = 1 / 0.25 = 4x。

这意味着帧时间从 16ms 降到 4ms，剩下的 3.2ms（0.2 × 16ms）是串行瓶颈。

这是设计游戏引擎时必须面对的物理极限。

🔬 深入版

追问 1："memory_order 的 4 种模式怎么用？"

模式 保证 典型场景
relaxed 仅保证原子性，无顺序保证 计数器
acquire / release 成对使用：release 前的写入对 acquire 后可见 生产者-消费者、锁的实现
seq_cst 全局顺序一致性（默认、最安全最慢） 不确定时用这个

追问 2："为什么无锁队列难写？"

因为 ABA 问题：线程 A 读到 head 指针 → 被切走 → 线程 B 弹出两个元素，又 Push 回一个 → head 指针地址相同但内容变了 → 线程 A 的 CAS 比较地址，发现没变，成功——但实际已经错了。

解法：Tagged Pointer（指针高位加版本号）或 Hazard Pointer。

追问 3："协程 vs 线程，在游戏里怎么选？"

  • 协程：在主线程上模拟异步，无上下文切换开销，适合"等待下一帧"、"等待加载完成"。Unity Coroutine
  • 线程：真正并行，适合计算密集型任务（寻路、物理）。Unity Job System 就是封装好的线程池

关键区别：协程不能利用多核，线程可以。但协程更简单，没有线程安全问题。90% 的场景用协程+Job System 就够了，不需要手动管理线程。

Q6（行为面试）：你做过的最有挑战的性能优化是什么？

🕐 3 分钟版（用 STAR 法则）

Situation（背景）： 我负责设计一个 Rust 分布式游戏服务器框架（Ares），需要支持 100+ 并发连接的帧同步竞技。核心挑战是：帧同步要求每帧内所有玩家的输入到齐、逻辑计算完成、响应发回——必须在 16.6ms 内。

Task（任务）： 设计一个低延迟、高吞吐的分布式架构，同时保证帧同步的确定性模拟。

Action（行动）： 1. 架构设计：分层为 Gateway（连接管理）→ Game（逻辑）→ Room（状态）→ Battle（帧同步）→ Chat，每个服务独立进程，通过 gRPC async 通信。这样每个服务可以独立扩缩容，无锁竞争。 2. 网络层：用 Tokio 异步运行时 + Tonic gRPC。压测发现瓶颈在序列化——ProtoBuf 的序列化占了 30% 的帧时间。改用增量同步——不是每帧发完整状态，只发变化字段——带宽从 15KB/s 降到 3KB/s。 3. 帧同步引擎：实现 Fixed Timestep 循环，帧逻辑与渲染解耦。用 Xorshift 确定性随机数替代系统 rand。关键操作的执行顺序明确编码（先碰撞再技能），保证跨平台一致性。

Result（结果）： - 压测：3 轮（50/200/100 连接），零超时零错误 - 最高吞吐：3,485 RPS - 平均延迟：28.68ms - 5 个服务独立编译成功，cargo test --workspace 36/36 全部通过

学到了什么：性能优化的 80% 在架构层面，20% 在代码层面。如果一开始架构就有锁竞争，后面再优化也是事倍功半。

📊 10 分钟版（加了设计决策的"为什么"）

（接 3 分钟版，追加技术决策的深度解释）

为什么选 Rust？ - 无 GC：帧同步对停顿零容忍 - 零成本抽象：async/await 编译为状态机，无运行时开销 - 所有权模型：编译期消除数据竞争，多线程不需要锁就能安全共享数据

为什么用 gRPC 而不是自定义 TCP 协议？ - gRPC 自带负载均衡、健康检查、流控 - Protobuf 比 JSON 的序列化快 5x，且零拷贝的部分可以用 FlatBuffers 补充 - 但缺点也很明显：HTTP/2 的头部开销在帧同步场景下不可忽视。如果重新设计，我会在 Battle Service 内部用自定义 UDP 协议 + KCP

最大的坑和怎么解决的： - 问题：TCP 的 Head-of-Line Blocking——一个包的延迟阻塞后续所有包 - 解决：Gateway 和 Game 之间用 HTTP/2 多路复用（gRPC 内置），Battle 内部计划用 UDP

如果可以重新做： - 帧同步引擎用 ECS 架构改写，Component 连续存储，Cache 友好 - Battle Service 的网络层从 gRPC 切换到 QUIC/WebTransport
